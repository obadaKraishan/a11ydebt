**The one difference, and why: RNG stream position.**
- **AISSA:** all four intervals come from **one shared generator**. Each interval therefore depends on everything drawn before it; Rico's interval depends on AndroidControl's data, for example.
- **`a11ydebt report`:** each interval gets **its own generator** seeded 20260908. A corpus's intervals then never depend on what else is in the report.
- **What matches:** AISSA's first draw (AC screen) is the same either way. The other three move by Monte Carlo noise only.
- **Method otherwise identical:** the algorithm, clusters, order, resample count and seed are all the same.

| needs_label interval | Paper (shared stream) | `a11ydebt report` (own generator) | Difference |
|---|---:|---:|---:|
| AC (10 shards), screen | [56.99, 57.53] | [56.99, 57.53] | none |
| AC (10 shards), app | [55.65, 58.86] | [55.66, 58.84] | ≤0.02 pp |
| Rico, screen | [17.50, 17.97] | [17.49, 17.98] | 0.01 pp |
| Rico, app | [17.14, 18.37] | [17.12, 18.37] | 0.02 pp |

- **Speed:** drawing in blocks is bit-identical to AISSA's loop but **no faster**: about 1.2 s for 5,000 × 60,637 clusters. AISSA's loop was already vectorized inside each resample, and exact reproduction needs the same 303M index draws. The full three-corpus report (18 intervals) takes 11.6 s.

## 6. Problems and how you handled them
1. **There is no bootstrap in AISSA's `src/a11ydebt/bootstrap.py`.** That file is an import shim that puts `src/` on `sys.path`. The cluster bootstrap is `cluster_bootstrap_rate` and `pct_ci` in `phase4_validation/03_reviewer_checks.py` (Check 1), so I ported those, plus `wilson_ci` from `stats.py`. `NOTICE` says so.
2. **The shared RNG stream.** AISSA's intervals share one generator, so three of the four can't be reproduced by a per-corpus report. I kept per-interval seeding in `report`, and put the exact reproduction in `compare_aissa.py bootstrap` (section 3b). Decision 1 below asks you about this.
3. **Floating point in the percentile.** `(1 - 0.95) / 2` is `0.025000000000000022` in floating point. I round it to AISSA's literal 0.025 and 0.975, so the percentiles are bit-identical. A test covers this.
4. **Vectorizing did not speed things up** (section 3b). It is still about 1.2 s per Rico screen-level interval, which is fast enough.
5. **Rico screens with no app.** AISSA drops them from the app-level bootstrap; a11ydebt makes each one its own cluster, to match the AndroidControl rule. Rico has **0** such screens, so the two rules give identical clusters (8,904).
6. **Commit order slip.** `d58309d` (the replay) imports `a11ydebt.report`, which only arrived in the next commit (`66d444a`, about 10 minutes later). Checking out `d58309d` alone would make that script fail to import. The library and tests were fine at every commit.
7. **numpy becomes a runtime dependency.** CLAUDE.md said pydantic was the only runtime dependency. The prompt asks for vectorized numpy, so I added `numpy>=1.26` and updated CLAUDE.md.
8. **Run 2 was still RUNNING at the start of the session** (19:24 UTC, on shard 00017). I built Part C meanwhile and pulled the run after it completed (around 19:33 UTC).
9. **The Rico audit was re-run** (368 s) so that `data/interim/audit_rico` matches the current code and the documented commands. It is still exact against AISSA.
